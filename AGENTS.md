# AGENTS.md — Guidance for AI Agents

This file guides agents making or reviewing changes in this repository. Read it before editing.

## Project context

- Nyx Fit: mobile-first workout tracking PWA (React 19 + TypeScript strict + TanStack Router file-based routes + Tailwind v4 + framer-motion, Cloudflare Workers + D1 + R2 backend).
- Fonts: Chakra Petch (headings, automatic via `h1..h6` in `src/styles.css`) and Titillium Web (body).
- Backend: Cloudflare D1 through TanStack server functions (`src/lib/api/functions.ts`), private R2 image routes, better-auth via `authClient` (`src/lib/auth-client.ts`), profile persistence via `useUpsertCurrentProfile` (`src/lib/api/hooks.ts` — hook takes NO arguments, returns `{ upsertCurrentProfile }`; the mutation takes `{ updates }`). Use Bun for installs and project commands. Bindings are in `wrangler.jsonc`, migrations in `src/db/migrations/`, local secrets in `.dev.vars` (see `.dev.vars.example`).
- **Before changing workouts, stats, auth origins or the build, read `docs/data-invariants.md`** and update it when you add or close a gap.
- `src/routeTree.gen.ts` is auto-generated by `@tanstack/router-plugin` during dev/build. NEVER hand-edit it; run dev/build after adding route files.
- Colours: use semantic tokens (`docs/light-mode.md` §4); never raw `text-white`/`bg-zinc-*`/`bg-white/*` or colour literals in framer `animate`. `text-white` is only for text on saturated fills (brand, emerald, red, orange gradients).

## Design Context

### Users
Nyx Fit serves multiple user types: beginners, intermediate lifters, advanced athletes, and coaches. The product should identify the user's level during profile creation after login, then tailor the experience to that mode's philosophy, defaults, and feature emphasis. The mode must remain switchable in settings. Across all modes, the primary job to optimize is fast workout logging with minimal friction on mobile.

### Brand Personality
Nyx Fit should feel powerful, precise, and playful. The interface should mainly evoke confidence and focus, with room for future mood variations that can later become user-selectable. The tone should feel performance-oriented and modern without becoming macho, noisy, or gimmicky.

### Design Principles
1. Thumb reachability is the core pillar: primary actions sit in the bottom two-thirds of the screen, where a one-handed thumb can reach them.
2. Optimize every core flow for rapid mobile workout logging before adding visual or feature complexity.
3. Design one shared system that adapts by user mode, so beginners get guidance while advanced users and coaches retain speed and control.
4. Make the product feel confident and performance-driven through clear hierarchy, strong contrast, and deliberate motion rather than visual noise.
5. Meet WCAG AA expectations and support reduced-motion accommodations as a default quality bar.

## Hard rules (all agents)

1. **No commits** unless the user explicitly asks.
2. **No new dependencies** without explicit user approval. Check `package.json` before assuming a library exists.
3. **Match existing conventions**: named exports (no default exports), `type` aliases over `interface`, string-literal unions over TS enums, existing Tailwind class recipes and import ordering. Read the relevant implementation, callers and tests before editing.
4. **TypeScript strict is on.** No `any` or blind `as` casts. Use simple literal unions or keyed records for finite steps; use discriminated unions when variants carry different data and make switches exhaustive (`satisfies never`). Parse external/untrusted input (storage, JSON) with type guards, never a bare cast.
5. **A11y bar**: WCAG AA (4.5:1 text, 3:1 non-text), ≥44px touch targets, full keyboard support (prefer native elements over ARIA-recreated patterns), `prefers-reduced-motion` respected in BOTH CSS and framer-motion (`MotionConfig reducedMotion="user"`). For step changes, move focus to the new heading.

## Implementation style

- Prefer the smallest complete flow. In multi-step UI, keep navigation in one coordinator, screen markup in focused components, and session/persistence effects in a hook when that makes ownership clearer. Keep one-use copy and values near their use; share UI or class recipes only for real repetition.
- Keep persisted drafts consistent with the active path. Onboarding setup and existing-account sign-in must not replay each other's draft or save a profile from stale intent. Keep auth callback, retry and redirect paths intact when simplifying.
- When replacing a flow, compare surviving user-visible behavior with the old implementation and tests. Keep a few focused tests for critical transitions and failure/retry paths; passing tests do not compensate for deleting coverage of behavior that still exists.
- After simplification, check callers for unused exports, routes, config and assets. Use one canonical public asset path; report remaining orphans rather than expanding the change without approval.

## Tool privileges

- **Browser work uses only the agent-browser skill and cli**
- **Research/reviewer agents have web access**: use `websearch` for industry data, benchmarks, and current practices; use `webfetch` to read specific articles/docs. Do not claim "web unavailable" without attempting both. Cite source URLs in all research output.
- **Reviewer agents may read any repo file** to verify claims, but must not modify anything.
- **Planner agents may read any repo file** but must not modify anything.
- **Implementor agents write code** and MUST verify with the repo's build/typecheck command (see `package.json` scripts) before finishing.
- File writes outside `src/` and `docs/` need user approval.

## Working pipeline (SDLC)

Scale the process to the change: inspect the tracked and untracked diff → make the smallest complete edit → run relevant checks → review behavior and the final diff. For large or high-risk work, add research, a plan, review and human approval before implementation.

- Classify review findings: **P0** (breaks core flow/data loss), **P1** (major bug, wrong behavior on a common path), **P2** (should fix, non-blocking), **P3** (nice-to-have). Surface P0/P1 findings before approval or commits and re-review if fixed; record P2/P3 without inventing blockers.
- Review correctness, retained behavior and maintainability. Look for one-use abstractions, duplicate assets, stale configuration and tests removed without replacement; a smaller line count alone is not evidence of a simpler, working feature.

## Reporting requirements (every subagent)

End every task with a structured summary containing:

1. What was done (files touched / findings).
2. **Problems & blockers encountered** — call these out explicitly in a dedicated section. Never silently work around a blocker. If a claim could not be verified, say so.
3. Assumptions made and their confidence.
4. Verification evidence (build output, test results, or "read-only task, no build run").

## Escalation

If a task requires schema/backend changes, new auth providers, new dependencies, deleting user files, or contradicting applicable repository instructions, stop and surface it to the orchestrator instead of proceeding.
