# AGENTS.md — Guidance for AI Subagents

This file is the operating contract for any AI subagent (research, planner, reviewer, fixer, implementor) working in this repository. Read it fully before doing anything.

## Project context

- Nyx Fit: mobile-first workout tracking PWA (React 19 + TypeScript strict + TanStack Router file-based routes + Tailwind v4 + framer-motion, Convex backend, Capacitor iOS wrapper).
- Design principles, product goals, and UX tone live in `CLAUDE.md` — read it before any design or copy work.
- Fonts: Chakra Petch (headings, automatic via `h1..h6` in `src/styles.css`) and Titillium Web (body). Dark mode is forced (`<html class="dark">`).
- Backend: Convex (`convex/`), better-auth via `authClient` (`src/lib/auth-client.ts`), profile persistence via `useUpsertCurrentProfile` (`src/lib/convex/hooks.ts` — hook takes NO arguments, returns `{ upsertCurrentProfile }`; the mutation takes `{ updates }`).
- `src/routeTree.gen.ts` is auto-generated by `@tanstack/router-plugin` during dev/build. NEVER hand-edit it; run dev/build after adding route files.

## Hard rules (all subagents)

1. **No commits** unless the user explicitly asks.
2. **No new dependencies** without explicit user approval. Check `package.json` before assuming a library exists.
3. **No code comments** and **no emojis** in UI or code, unless the surrounding file's established style does otherwise.
4. **Match existing conventions exactly**: named exports (no default exports), `type` aliases over `interface`, string-literal unions over TS enums, existing Tailwind class recipes, existing import ordering. Read 2–3 neighboring files before writing anything.
5. **TypeScript strict is on.** No `any`, no blind `as` casts, discriminated unions for state machines, exhaustive switches (`satisfies never` in default branch). "Parse, don't validate" for any external/untrusted input (storage, JSON): hand-written type guards, never a bare cast.
6. **SSR awareness**: this is a TanStack Start app — guard all `window`/`sessionStorage`/`localStorage` access with `typeof window !== "undefined"` and never run it during server render.
7. **A11y bar**: WCAG AA (4.5:1 text, 3:1 non-text), ≥44px touch targets, full keyboard support (prefer native elements over ARIA-recreated patterns), `prefers-reduced-motion` respected in BOTH CSS and framer-motion (`MotionConfig reducedMotion="user"`).

## Tool privileges

- **Research/reviewer agents have web access**: use `websearch` for industry data, benchmarks, and current practices; use `webfetch` to read specific articles/docs. Do not claim "web unavailable" without attempting both. Cite source URLs in all research output.
- **Reviewer agents may read any repo file** to verify claims, but must not modify anything.
- **Planner agents may read any repo file** but must not modify anything.
- **Implementor agents write code** and MUST verify with the repo's build/typecheck command (see `package.json` scripts) before finishing.
- File writes outside `src/`, `docs/`, and `convex/` need user approval.

## Working pipeline (SDLC)

Research → Plan → Review → Fixer → Re-review loop → Human approval → Implement.

- Every review must classify findings by severity: **P0** (breaks core flow/data loss), **P1** (major bug, wrong behavior on a common path), **P2** (should fix, non-blocking), **P3** (nice-to-have).
- The re-review loop repeats (review → fix → review) **until no P0/P1 findings remain**. P2/P3 findings are recorded and passed to the implementor as non-blocking notes. Be realistic: if a cycle produces no new P0/P1 findings, stop the loop — do not manufacture blockers.
- Reviews must cover correctness/major bugs (P0–P1) as well as quality (P2–P3). Additionally, run a **ponytail over-engineering pass** (`delete:/stdlib:/native:/yagni:/shrink:` findings, `net: -N lines`) on plans and diffs.
- Fixers must address every blocking finding and state what was done for each.
- The human approval artifact (e.g., explainer HTML) is produced ONLY after the review loop converges (no P0/P1).

## Reporting requirements (every subagent)

End every task with a structured summary containing:

1. What was done (files touched / findings).
2. **Problems & blockers encountered** — call these out explicitly in a dedicated section. Never silently work around a blocker. If a claim could not be verified, say so.
3. Assumptions made and their confidence.
4. Verification evidence (build output, test results, or "read-only task, no build run").

## Escalation

If a task requires: schema/backend changes, new auth providers, new dependencies, deleting user files, or anything contradicting `CLAUDE.md` — stop and surface it to the orchestrator instead of proceeding.
