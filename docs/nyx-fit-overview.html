1 What Nyx Fit Is Now

Nyx Fit is a mobile-first workout logger — create workouts, log sets fast, track weight, review history, and follow progress. Optimized for thumb-reach, dark-first, with orange/cyan accents. It serves beginners through coaches, and the plan is to adapt the experience by user mode (still only a stored field today).

What ships today

Built

Workout Logging

Start/continue workouts, body-part picker with "last worked" memory, live session timer, rest timer with vibration + notifications, set drawers with duplicate & auto-increment, exercise wheel-picker with category inference.

Built

Auth

Better Auth via Convex component — passwordless email + Google sign-in, SSR session bootstrap, secure cookie handling.

Built

Weights & Goals

Weight log with W/M/Y chart, 5-per-page history, progress photos, lbs/kgs conversion (canonical lbs). Goal reference line exists in schema but has no UI to set it.

Partially Built

Stats

Workout summary (totals, streaks) is live. Exercise Records & Weekly Volume Trend read a table nothing writes — they render empty for every user.

Built

Settings & Profile

Profile (name, gender, unit, fitness level, avatar), appearance (font theme, attendance card style, rest timer, weekly goal) in localStorage, legal pages, logout.

Partial

Home

Greeting, weekly attendance (3 display variants), quick actions, start-workout card. Recent-workouts list is code-complete but commented out.

Built

PWA

Manifest, icons, install prompt, offline banner, custom Workbox service worker, Lighthouse PWA 100.

Scaffolded

Mobile Shells

Android TWA (Bubblewrap, CI-ready) and iOS Capacitor wrapper — both are remote shells loading the deployed PWA. No native app logic.

3 Architecture View

One deployable web app + two thin mobile shells. Everything lives on one origin: fit.webdevsam.pro.

System layers

DeployVercel (SSR), Convex cloud (data), GitHub Actions (Android APK/AAB)

Data model

Five tables, all joined by userId (no FKs — the better-auth user id). Exercises & sets are embedded inside the workout document.

profiles

name, email, gender, avatar, fitnessLevel (the "mode" — stored, never read), weightUnit (lbs/kgs), notifications.

workouts

date, duration, isActive, exercises[] (name + sets[] of weight/reps), bodyParts, notes.

weightEntries

date, weight (canonically lbs), note, optional photo (Convex storage).

weightGoals

targetWeight, weeklyGoal, startWeight/date. No setter UI exists.

exerciseStats

Pre-aggregated per exercise: totals, PRs, 12-week rolling history. Writer is dead code.

Auth flow

login.tsx→ authClient.signIn.email / Google→ better-auth route via /api/auth/$→ cookie on web origin→ SSR fetchAuth → setAuth(token)→ Convex queries authorized
  • Sign-in is passwordless email (empty password) + Google OAuth. No password UI exists.
  • Android TWA shares the same origin/cookies; iOS WKWebView is the least-tested surface.
  • No global route guard — several pages check session manually, some don't check at all.

Core flow trace — workout logging

Home → WorkoutStatusCard (body part)→ api.workouts.startWorkout→ /workout/:id live timer→ AddExerciseDrawer + SetDrawer→ api.workouts.updateWorkout (patch whole exercises array)→ End → isActive false + duration

Realtime via Convex useQuery. Note two unit-handling surfaces: additions convert to lbs at the boundary, but SetDrawer edits store the raw display-unit number — a kgs user's sets can end up mixed-unit.

Design system

Tailwind 4 + shadcn/ui (new-york, zinc) + token-driven theming, framer-motion for motion, wheel pickers (@ncdai/react-wheel-picker) for native-iOS-feeling inputs. Dark-first: html.dark is hardcoded — light mode is nominal. Orange/cyan accents, purple primary, red reserved for destructive.

4 Health & Biggest Risks

Good

Core architecture is sound

Route → typed hook → Convex function is a clean, testable layering. Smart shells strategy (one PWA, two wrappers) is minimal and well-documented. Docs match code unusually well.

Risk

Two codebases, no decision

TanStack web app vs. Expo rewrite (expo-app branch). Both ship overlapping features; no documented plan for which is canonical.

Risk

Branch labyrinth

4 stacked feature branches, none merged (foundation → core-logging → dev-opencode → stats spike). Merge requires mode-vocab migration + stats resolution.

Risk

Half-implemented features

Exercise stats never written, weight-goal UI missing, mode field unused, set editor unit conversion broken for kgs users, some reads lack ownership checks.

Blocked

Stores gated by humans

Keystore secrets, Apple developer account, Convex prod deploy verification — the code is ready, the accounts/secrets are not.

Highest-value next moves (recommendation): 1) merge the foundation + core-logging chains in one pass and resolve the mode-vocab migration; 2) make exercise-stats writes real or delete the table; 3) centralize the lbs/kgs conversion at one boundary; 4) prune dead code (weightEntries.ts, auth-server, template leftovers); 5) pick the canonical codebase between web and Expo before building more features on both.
