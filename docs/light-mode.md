# Light mode: addition guide

This guide adds a user-selectable **Light / Dark / System** colour mode to Nyx Fit. It covers the decisions, the token system, the class migration map, the rules for colours written in JS, and a phased execution plan with acceptance checks for each phase. The phases are written so an implementing agent can take one phase at a time.

It assumes the rules in `AGENTS.md`: strict TypeScript, named exports, WCAG AA, reduced motion, no new dependencies, and never editing `src/routeTree.gen.ts`.

---

## 1. Where we are today

- **The dark look is hard-coded.**
  - `src/routes/__root.tsx` renders `<html lang="en" className="dark">`.
  - `src/styles.css` already has a full shadcn-style semantic token set. The light values live in `:root` and the dark values in `.dark`. Both are bridged to Tailwind in `@theme inline`, so `bg-background`, `text-foreground`, `bg-card`, `border-border`, `text-muted-foreground` and friends already exist.
- **The main app mostly ignores those tokens.** It uses raw dark utilities instead. Approximate counts across `src/`:

  | Utility | Count |
  |---|---|
  | `text-white` | 130 |
  | `text-zinc-*` | 141 |
  | `bg-white/*` | 98 |
  | `border-white/*` | 61 |
  | `bg-zinc-9xx` | 50 |
  | `bg-zinc-8xx` | 24 |
  | `bg-black*` | 25 |
  | gradients from dark stops | ~200 |

- **`--color-black` is aliased to the page background.** `src/styles.css` sets `--color-black: var(--background)`, so every `bg-black`, `bg-black/60`, `from-black` and `text-black` means "background colour" rather than black. In light mode this alias would turn scrims white and make `text-black` checkmarks invisible. It has to be removed, and each `black` usage re-classified first (see §5.3).
- **Colours also live in JS**, where CSS tokens can't reach them:
  - framer-motion `animate` values in `src/components/dock/ActionDock.tsx` and `src/components/dock/StartDrawer.tsx`;
  - recharts `fill`/`stroke` literals in `src/components/weights/WeightChart.tsx`;
  - inline `style={{ "--c": "#f97316" }}` in `src/routes/stats.tsx` and `src/routes/weights.tsx`;
  - `iconColor` hex values in `src/config/navigation.ts`;
  - arbitrary `shadow-[…rgb(0_0_0/…)]` classes.
- **Appearance preferences** (`src/lib/AppearanceContext.tsx`) are font theme, attendance variant and rest timer. They're persisted to `localStorage` and applied in `useEffect` after first paint, so a non-default font can flash on load. There is no colour mode.
- **Head and PWA colours:**
  - `theme-color` meta is `#000000` (`__root.tsx`).
  - `apple-mobile-web-app-status-bar-style` is `black-translucent`.
  - The manifest is generated by VitePWA in `vite.config.ts` (`theme_color` and `background_color` are `#000000`).
- **Separate "worlds" that stay as they are:**
  - `.theme-onboarding` and `.theme-flow` (light) and `.theme-night` (dark) re-declare the whole token set for onboarding and loading.
  - The `src/routes/design.*` playground.
  - Neither is part of this work.
- **Unused code:**
  - `src/components/FontThemeContext.tsx` duplicates the font-theme logic and has no importers.
  - `src/components/ui/sonner.tsx` imports `next-themes`, but it is never mounted, and `next-themes` has no provider.
  - Report both, but don't delete them as part of this work.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | The mode is `"system" \| "light" \| "dark"`, and **the default is `"dark"`**. | Dark is the brand (Night Runner). Existing users see no change until they opt in. Changing the default later is a one-line edit in `src/lib/color-mode.ts`. |
| D2 | The mode is persisted **only in `localStorage`** (`nyx-color-mode`), per device. | It's a display preference, it costs nothing in D1 (D1 cost matters), and it must be readable before first paint, which a server round-trip can't be. |
| D3 | It's applied as the **`.dark` class on `<html>`**, set by an inline script before first paint. | `@custom-variant dark (&:is(.dark *))` and the `.dark { … }` token block already exist. A pre-paint script is the only way to avoid a flash on SSR pages. |
| D4 | **Semantic tokens do the work, not `dark:` variants.** Components use `bg-card`, `text-foreground`, `bg-fill` and so on. `dark:` pairs are allowed only for one-off accent colours (§4.4). | One source of truth. Future moods (AGENTS.md: "room for future mood variations") become new token blocks, not new class soup. |
| D5 | **Framer-motion never animates a colour literal.** Colour comes from a token class on a layer, and motion animates `opacity` (or geometry). | Inline colour values ignore theme changes and can't read tokens. Opacity is cheaper to animate as well. |
| D6 | The toggle lives in **Settings → Appearance**, as the first group, as a 3-option segmented control built from native radio inputs. | It's a discoverable, keyboard-native control that sits with the other appearance options. |
| D7 | The mode switches instantly. Transitions are suppressed for one frame while the class flips. | This avoids hundreds of elements animating `transition-colors` at once. An optional View Transition crossfade is listed in §8. |
| D8 | Onboarding worlds, `design.*` routes and brand marks (`GoogleColorMark`) are **out of scope**. | They define their own palettes on purpose. |

## 3. Architecture

### 3.1 `src/lib/color-mode.ts` (new, pure, unit-tested)

```ts
export type ColorMode = "system" | "light" | "dark";
export type ResolvedColorMode = "light" | "dark";

export const COLOR_MODES = ["system", "light", "dark"] as const satisfies readonly ColorMode[];
export const DEFAULT_COLOR_MODE: ColorMode = "dark";
export const COLOR_MODE_STORAGE_KEY = "nyx-color-mode";
// Must match --background for each mode in src/styles.css.
export const THEME_COLOR: Record<ResolvedColorMode, string> = { light: "#fafafa", dark: "#09090b" };

export function isColorMode(value: unknown): value is ColorMode { … }          // type guard, no casts
export function parseColorMode(raw: string | null): ColorMode { … }             // falls back to DEFAULT_COLOR_MODE
export function resolveColorMode(mode: ColorMode, prefersLight: boolean): ResolvedColorMode { … }
export function applyColorMode(resolved: ResolvedColorMode): void { … }         // toggles .dark on <html>, updates meta[name=theme-color]

// Inline, dependency-free copy of parse + resolve + apply, run in <head> before paint.
// Keep it in sync with the functions above; a unit test evaluates it against them.
export const COLOR_MODE_SCRIPT = `(function(){try{…}catch(e){}})()`;
```

- `applyColorMode` must:
  - toggle `document.documentElement.classList` `dark`;
  - set `meta[name="theme-color"]`'s `content` to `THEME_COLOR[resolved]`;
  - suppress transitions for one frame: add a `.color-mode-switching` class to `<html>`, force a style flush (`getComputedStyle(...).opacity`), and remove it on the next `requestAnimationFrame`. It must not be called during SSR.
- `COLOR_MODE_SCRIPT` must:
  - read `localStorage` inside `try` (it can throw in private mode);
  - treat anything unknown as `DEFAULT_COLOR_MODE`;
  - use `matchMedia('(prefers-color-scheme: light)')` for `system`;
  - toggle `.dark` and update the theme-color meta.
- Tests (`src/lib/color-mode.test.ts`):
  - the guard and parser reject `null`, `""`, `"DARK"` and `"sepia"`;
  - `resolveColorMode` covers all three modes with both OS preferences;
  - running `COLOR_MODE_SCRIPT` with `new Function(...)` against a jsdom `document` agrees with `resolveColorMode` for each stored value, including storage throwing.

### 3.2 Pre-paint wiring in `src/routes/__root.tsx`

- Keep `className="dark"` on `<html>`. It's the correct server default because `DEFAULT_COLOR_MODE` is dark. Add `suppressHydrationWarning` to `<html>`, because the script may have changed the class before hydration.
- Inject `COLOR_MODE_SCRIPT` in `<head>` **right after `<HeadContent />`** (so the theme-color meta it updates already exists; a parser-inserted inline script still runs before first paint), with `<script dangerouslySetInnerHTML={{ __html: COLOR_MODE_SCRIPT }} />`. 
- Keep the `theme-color` meta but set its initial `content` to `THEME_COLOR.dark`. The script rewrites it before paint.
- Check that no CSP header blocks inline scripts. Search `wrangler.jsonc`, `src/server*` and any response-header middleware for `Content-Security-Policy`. If one exists, stop and report it: it needs a hash or nonce, and that's a user decision.

### 3.3 `AppearanceContext`

- Add `colorMode: ColorMode`, `resolvedColorMode: ResolvedColorMode` and `setColorMode(mode)`.
- On mount, read the mode with `parseColorMode(localStorage.getItem(...))` inside `try`. The initial state must be `DEFAULT_COLOR_MODE` so the server and client first render agree.
- When `colorMode` changes:
  - persist it (inside `try`);
  - resolve it;
  - call `applyColorMode`.
- While the mode is `"system"`, subscribe to `matchMedia('(prefers-color-scheme: light)')` `change` events and re-apply. Unsubscribe on cleanup.
- Replace the existing blind casts (`as FontTheme | null`) with small type guards in the same style, and give `restTimerDuration` a NaN guard. It's the same file and the same parsing rule from AGENTS.md.
- Update the context mock in `src/routes/settings.test.tsx` to include the three new fields.

### 3.4 CSS additions in `src/styles.css`

1. **`color-scheme`**, so native controls, scrollbars and autofill follow the mode:
   ```css
   :root { color-scheme: light; }
   .dark { color-scheme: dark; }
   .color-mode-switching, .color-mode-switching * { transition: none !important; }
   ```
2. **App tokens.** Extend `:root` (light) and `.dark` (dark) with the tokens in §4, and bridge them in `@theme inline`. For example: `--color-fill: var(--fill);`, `--color-ink-secondary: var(--ink-secondary);`, `--shadow-float: var(--elev-float);`.
3. **Retune the existing light values** in `:root` to the §4.1 table. The shadcn defaults (white background, near-black primary) are not the Nyx look.
4. **Do not touch** `.theme-onboarding`, `.theme-flow` or `.theme-night`.

### 4.4 One-off accents (cyan, orange, rose, violet…)

Some accents appear only a few times: the cyan typography picker, orange weight accents, and stats colours. Don't mint a token for each. Use a paired utility instead:

- text on a neutral or tinted surface: `text-X-700 dark:text-X-300` (or `-400`, whichever the dark value was);
- tints: `bg-X-500/10 dark:bg-X-900/20`;
- lines: `border-X-600/40 dark:border-X-500/50`.

`X-700` on white passes AA for every Tailwind hue except yellow, amber and lime. For those, use `-800`.

### 5.3 Removing the `--color-black` alias (last step of the migration)

Only after every `bg-black*`, `from-black`, `to-black` and `text-black` in scope has been classified with §5.1:

1. Delete `--color-black: var(--background);` from `@theme inline`.
2. `grep -rn "black" src --include=*.tsx | grep -v "routes/design\|onboarding"`. Every remaining hit must mean literal black on purpose; justify any that remain in the phase report.

### 5.4 Head and PWA

- `theme-color`: this is handled dynamically by `applyColorMode` and the pre-paint script.
- `apple-mobile-web-app-status-bar-style: black-translucent`: iOS reads it only at launch and always draws **white** status-bar text. In light mode the clock sits on a light background. Keep the value for now and record it as a known gap to test on a device. It is a user decision (§9).
- Manifest `theme_color`/`background_color` (`vite.config.ts`) stay `#09090b`. The splash is brand-dark by design, and the manifest cannot vary by mode.
